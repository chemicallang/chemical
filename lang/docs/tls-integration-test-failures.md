## Applied Fixes

### 1. Added `set_blocking` to net library

**File**: `lang/libs/net/posix/platform_api.ch`

```chemical
public func set_blocking(s: Socket) {
    var flags = fcntl(s as int, F_GETFL, 0);
    fcntl(s as int, F_SETFL, flags & ~O_NONBLOCK);
}
```

### 2. `ssl_set_socket` ensures blocking mode

**File**: `lang/libs/tls/src/ssl.ch`, line ~3712

```chemical
public func ssl_set_socket(ssl : *mut SSLContext, socket : net::Socket) {
    ssl.transport_socket = socket
    ssl.transport_connected = true
    net::set_blocking(socket)  // ADDED
    ssl.major_ver = 3
    ssl.minor_ver = 3 as u8
    ssl_apply_recv_timeout(ssl)
}
```

**Rationale**: The server tests set `net::set_nonblocking(server_sock)` for the accept loop. The accepted `client_sock` inherits non-blocking mode. The SSL implementation uses `recv_all` which does a single `recv` syscall → returns -1 (EAGAIN) on empty non-blocking socket → Chemical interprets as `ERR_SSL_CONN_EOF`. This fix makes the client socket blocking so `recv` blocks until data arrives.

**Why `recv_all` is dangerous**: `lang/libs/net/src/main.ch:138` — `recv_all` does exactly ONE `recv()` syscall. Despite its name, it does NOT read all bytes. It returns whatever one `recv` produces. On blocking sockets it blocks for data; on non-blocking sockets it immediately returns EAGAIN.

### 3. Double seq_num increment (already fixed by `fb854dbb7`)

The commit `fb854dbb7 tls library fixes` already removed the duplicate `ssl_incr_seq_num()` at `ssl.ch:1443` that was added by commit `2ce63bfb`. The increment at line ~1450 (guarded by `ssl.tls_version < SSL_VERSION_TLS1_3`) is sufficient for TLS 1.2.

## Detailed Wire-Level Analysis (INT_tls13_server_client)

### Wire bytes captured via `printf` in `ssl_send`/`ssl_recv`

**Chemical server sends (6 TLS records — all format-valid):**

```
Record 1 — ServerHello (plaintext):  160303007a 0200007603...  (127 bytes total)
Record 2 — CCS (plaintext):          1403030001 01              (6 bytes total)
Record 3 — EncryptedExtensions:      1703030017 <ct+tag:23>    (28 bytes total)
Record 4 — Certificate (empty):      1703030019 <ct+tag:25>    (30 bytes total)
Record 5 — Finished:                 1703030021 <ct+tag:33>    (38 bytes total)
```

**Python client sends (1 response before disconnecting):**

```
Record — ALERT:  1503030002 02 32   (fatal, decode_error=50)
```

### What the alert tells us

Python sends a **FATAL alert with description 50 = DECODE_ERROR**. This means Python couldn't decode a message (field out of range or length incorrect). The alert arrives BEFORE the Chemical server finishes sending (interleaved with the Finished `ssl_send`). This means Python fails DURING processing of the server's messages, NOT during the client's own send (no Finished/CCS is sent by Python).

### Comparison: Working vs Failing ServerHello

**Working** (Python server → Chemical client, from `INT_tls13_client`):
```
160303 005a     // record: CT=22, len=90
02000056        // handshake: type=2, body_len=86
0303<rand32>    // version + random
00              // session_id_len = 0 (EMPTY)
1301            // cipher = TLS_AES_128_GCM_SHA256
00              // compression
002e            // extensions_len = 46
  002b 0002 0304          // supported_versions FIRST
  0033 0024 <x25519:36>   // key_share SECOND
```

**Failing** (Chemical server → Python client, from `INT_tls13_server_client`):
```
160303 007a     // record: CT=22, len=122
02000076        // handshake: type=2, body_len=118
0303<rand32>    // version + random
20<sid:32bytes> // session_id_len = 32 (echos client's 32-byte session ID)
1301            // cipher = TLS_AES_128_GCM_SHA256
00              // compression
002e            // extensions_len = 46
  0033 0024 <x25519:36>   // key_share FIRST  ← order differs!
  002b 0002 0304          // supported_versions SECOND
```

### Differences found (none proven to be the cause)

1. **Session ID**: Python server sends 0-length. Chemical echoes client's 32-byte session ID. Tried forcing 0-length → no improvement.

2. **Extension order**: Python sends `supported_versions` first, Chemical sends `key_share` first. Extension order should not matter per RFC 8446.

3. **Message sizes**: Natural difference due to session ID echo. Length fields are correct.

4. **CCS**: Tried removing CCS entirely (optional in TLS 1.3) → no improvement. CCS message format is identical between working and failing.

5. **Record fragmentation**: Chemical sends record headers and bodies as separate `ssl_send` calls. Python server coalesces everything into one 658-byte TCP segment. Both should be handled fine by TCP.

6. **Extension encoding**: Byte-level verification shows all extension lengths and fields are correct.

## INT_tls12_client Failure Analysis

**Error**: `ERR_SSL_HANDSHAKE_FAILURE` — client verifies server's Finished verify_data, but it doesn't match.

**Root cause hypothesis**: Transcript hash mismatch. The transcript includes CH + SH + Certificate + ServerHelloDone + CKE. Python's server computes a different SHA-256 hash than Chemical's client.

**Negotiated cipher**: `TLS_RSA_WITH_AES_128_GCM_SHA256` (0x009C). Python supports this cipher in TLS 1.2 mode.

**Key area to audit**: The `ssl_hash_handshake_msg` function. The recent commit `2ce63bfb` changed from hashing `&raw hs_buf[0]` (with 4-byte handshake header) to `&raw hs_buf[4]` (body only, header is added by the function itself). Verify that ALL call sites pass `hs_buf[4]`, not `hs_buf[0]`. A single wrong call site would corrupt the transcript hash.

**ClientKeyExchange hashing**: At `ssl.ch:2847`, the CKE is hashed with `&raw cke_data[0]` where `cke_data` = `[key_len(2) + encrypted_pms(key_len)]`. Verify this matches Python's expected CKE body format (just the encrypted pre_master, no extra wrapping).

### Python HKDF verification script

```python
import hashlib, hmac, struct

def hkdf_extract(salt, ikm):
    return hmac.HMAC(salt, ikm, hashlib.sha256).digest()

def hkdf_expand_label(secret, label, context, length):
    hkdf_label = b"tls13 " + label.encode()
    struct_bytes = struct.pack(">HB", length, len(hkdf_label))
    struct_bytes += hkdf_label
    struct_bytes += struct.pack(">B", len(context))
    struct_bytes += context
    output = b""
    T = b""
    for i in range(1, 256):
        T = hmac.HMAC(secret, T + struct_bytes + bytes([i]), hashlib.sha256).digest()
        output += T
        if len(output) >= length:
            return output[:length]
    return output[:length]
```

This PROVES:
- RSA encryption/decryption of pre_master works correctly
- PRF (HMAC-SHA256 based) produces identical output
- Key block derivation produces identical output
- The mismatch is in the transcript hash (`hs_hash`) between the two sides

### ECDHE vs RSA Cipher — socat Trace Comparison

Used `socat -x` as TCP proxy. `openssl s_client -cipher 'ECDHE-RSA-AES128-GCM-SHA256:AES128-GCM-SHA256:@SECLEVEL=0'` successfully completes TLS 1.2 handshake with Python server. Python selects `ECDHE-RSA-AES128-GCM-SHA256` (0xC02F). The identical AES-128-GCM engine works correctly.

Chemical client ONLY offers `TLS_RSA_WITH_AES_128_GCM_SHA256` (0x009C) due to cipher filter (lines 1727-1733 of ssl.ch). The GCM engine is identical between these ciphers, yet Python's GCM decryption fails for the RSA variant. This is a STRONG clue that Python/OpenSSL's key block layout differs for non-PFS ciphers.

### TLS 1.2 Client — Next Investigation Step

The transcript hash (`hs_hash`) differs between Chemical client and Python server. The hash includes: ClientHello + ServerHello + Certificate + ServerHelloDone + ClientKeyExchange.

To find the exact mismatch, add SHA-256 hash computation at each `ssl_hash_handshake_msg` call and compare with a Python script that computes the same from captured wire bytes (using socat). The ClientKeyExchange body format is the most likely culprit: check if `cke_len` (258 = 2+256) matches Python's expected CKE body length.

### TLS 1.3 Server — New Hypotheses

1. Python 3.14's OpenSSL might REQUIRE a CertificateVerify signature even with `CERT_NONE` when the server has `own_cert` set. Try setting `own_key` from the PEM file.
2. The `supported_versions` extension in ClientHello has version `0301` in the record header but `0303` in the body. Check if this causes confusion.
3. Python might expect the EncryptedExtensions message to include specific extensions (like `server_name` if SNI was in ClientHello).
